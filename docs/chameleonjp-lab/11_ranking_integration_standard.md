# カメレオンJP ランキング連携共通規約 v1

最終更新: 2026-08-29  
規約版: `chameleonjp-ranking-standard-v1`  
対象: カメレオンJPの実験場へ登録する新規ゲーム、ランキングを追加・変更する既存ゲーム、実験場トップ、詳細ランキング、Supabase

## 1. この規約の位置づけ

この文書は、ランキング連携に関する最上位の共通規約です。

ランキング関連の作業では、最初にこの文書を読みます。既存の文書、ゲーム固有の文書、古いコード例と内容が食い違う場合は、この文書を優先します。ただし、ゲーム固有のスコア計算そのものは、各ゲームの仕様書を優先します。

この規約では、次の言葉を使います。

- **必須**: 守らない限り、実験場への登録または公開を完了扱いにしない。
- **禁止**: 新しい実装では使わない。既存実装に残っている場合は、変更時に移行対象とする。
- **推奨**: 原則として採用する。採用しない場合は理由を受入記録へ残す。

## 2. サイノメから得た教訓

サイノメでは、単独の設定ミスだけでなく、複数の食い違いが重なりました。

1. ソースコード、GitHub Pagesへ配備されたファイル、ブラウザのキャッシュが同じ版とは限らなかった。
2. 正式URL、試験用クエリ付きURL、Supabaseの`game_url`が混在した。
3. 同じJavaScriptモジュールを、クエリ付きとクエリなしの別URLで読み込み、同じ処理が別物として動く状態が生じた。
4. iPhone Safariでは、取り出した`fetch`関数の呼び方によって、Supabaseへ届く前に通信処理が失敗した。
5. 失敗表示、再送ボタン、実際の送信状態が、同じ状態情報から作られていなかった。
6. 過去の認証方式、受付番号方式、直接送信方式が同じリポジトリに残り、現行方式の判断が難しくなった。
7. `game_slug`、モード名、クライアント版、Supabase側の受付条件を、1か所で照合できなかった。

したがって、今後は「コードがある」「Supabaseへ行を登録した」「自動テストが通った」のどれか一つだけでは完成としません。ゲーム本体、配備物、Supabase、実験場、実機確認が同じ契約を使っていることを確認して、初めて完成とします。

## 3. ランキング連携の完成条件

ランキング連携は、次の6項目がすべて確認できた時だけ完成です。

| 確認対象 | 完成条件 |
|---|---|
| ゲームの仕様 | どの結果を、どの内部整数で、どの順序で競うか決まっている |
| ゲームのリポジトリ | `ranking-manifest.json`と実装値が一致している |
| 公開ページ | 正式URLで候補版が読み込まれ、対象版を識別できる |
| Supabase | ゲーム登録、受付処理、保存先、取得処理が契約と一致している |
| 実験場 | トップと詳細ランキングが同じ`game_slug`と表示設定を使っている |
| 本番確認 | iPhone Safariから実際に開始、終了、送信、再送、表示を確認している |

一つでも未確認、空欄、推測の項目があれば、完了扱いにしません。

## 4. 1ゲームにつき1つの連携定義を置く

各ゲームのリポジトリには、ランキング連携の設計値をまとめた`ranking-manifest.json`を置きます。

これは、人とコード作成ツールが同じ値を確認するためのファイルです。Supabaseの秘密情報は入れません。公開用キーも、このファイルには入れません。

定義の形式は、次のファイルを正とします。

- `docs/chameleonjp-lab/schemas/ranking-manifest-v1.schema.json`
- `docs/chameleonjp-lab/examples/ranking-manifest-v1.example.json`

### 4.1 役割の分担

値の正しさを一つに寄せすぎると、配備後の状態が見えなくなります。そこで、役割を分けます。

| 場所 | 役割 |
|---|---|
| ゲーム側の`ranking-manifest.json` | 作ろうとしている連携契約の正 |
| ゲーム側の実装 | マニフェストを実際に動かす処理 |
| Supabase `public.games` | 本番で現在使われている登録値 |
| 実験場トップ・詳細ページ | Supabaseの本番値を表示する側 |
| 受入記録 | マニフェストと本番値が一致した証拠 |

マニフェストだけを直してSupabaseを直さないこと、Supabaseだけを直接直してマニフェストを残さないことを禁止します。

### 4.2 単一モードと複数モード

URLの末尾と`game_slug`が同じである必要はありません。

一つのゲームURLに複数モードがある場合は、一つの`game_id`と一つの正式URLに対して、複数の`ranking_entries`を明示します。各モードは別の`game_slug`を持てます。

例:

- ゲームID: `sainome`
- 正式URL: `https://chameleonjp-lab.github.io/sainome/`
- ランキング識別子: `sainome_300_seconds`

`game_slug`をURLから推測して作ることを禁止します。マニフェストに書かれた値だけを使います。

## 5. 識別子の共通ルール

### 5.1 `game_id`

`game_id`は作品そのものを表す固定値です。

- 原則としてリポジトリ名と同じにする。
- 半角小文字、数字、アンダースコアだけを使う。
- 公開後は、表示名を変えても変更しない。
- 別作品として作り直す場合を除き、再利用しない。

### 5.2 `game_slug`

`game_slug`はランキングの保存単位を表します。

- `public.games.game_slug`、送信引数、ランキング取得引数で完全一致させる。
- 大文字小文字、アンダースコア、単数・複数、時間表記を勝手に変換しない。
- モードごとに分ける場合は、最初からすべて列挙する。
- スコアが存在する`game_slug`を、SQLの上書きだけで別名へ変更しない。
- 改名が必要な場合は、移行SQL、旧記録の扱い、実験場表示、ゲーム側の同時切替を一つの変更として行う。
- 廃止した`game_slug`をクライアントコード、試験、固定配列、再送キューに残さない。

### 5.3 `client_version`

`client_version`は、どのゲーム版から送られた記録かを表します。

- 1回の公開候補につき一つの値を使う。
- 送信処理を変えた場合は必ず更新する。
- 配備されたHTMLから確認できるようにする。
- 実装、マニフェスト、受入記録で完全一致させる。
- サーバー側で特定版だけを許可する場合は、ゲーム側の公開と同じ変更で切り替える。

## 6. 正式URLと配備版のルール

利用者と実験場が使う一つの正式なURLを、正式URL（canonical URL）と呼びます。

### 6.1 正式URL

正式URLは次を必須とします。

- `https://`で始める。
- ディレクトリ形式では末尾に`/`を付ける。
- `?v=...`などのクエリを含めない。
- `#...`を含めない。
- Supabase `public.games.game_url`、`<link rel="canonical">`、ホームのシェア、結果のシェア、実験場の「遊ぶ」リンクで完全一致させる。

試験時にクエリを付けても、保存、シェア、Supabase登録へは正式URLだけを使います。

### 6.2 配備版の識別

公開HTMLには、候補版を確認できる値を入れます。

```html
<meta name="chameleonjp-release" content="ゲームID-YYYYMMDD-NN">
<link rel="canonical" href="正式URL">
```

受入記録には、この値と候補コミットのSHAを残します。

### 6.3 JavaScriptとキャッシュ

同じJavaScriptファイルを、異なるURLとして同時に読み込むことを禁止します。

たとえば、次の二つを同じ画面内で混在させません。

```js
import './ranking-client.js';
import './ranking-client.js?v=20260819';
```

ブラウザはこの二つを別のモジュールとして扱うため、送信中フラグ、イベント、再送キューなどが二重に作られる可能性があります。

ビルド処理を使わないゲームでは、次を標準とします。

- HTMLから読む入口のCSS・JavaScriptには、公開版を表すクエリを付けてもよい。
- JavaScript内部の`import`は、同じファイルに対して常に同じ表記を使う。
- 内部モジュールへ個別のクエリを手作業で付けない。
- 内部モジュールを変更した場合は、入口ファイルの公開版を更新し、本番URLで新しい内容を確認する。
- より厳密なキャッシュ更新が必要なゲームは、すべての参照を自動生成できるビルド方式を使う。

## 7. プレイヤー名のルール

プレイヤー名はゲーム開始前に確定します。名前なしではランキング対象プレイを開始できません。

共通の最低条件は次です。

- 前後の空白を除いた後、1文字以上20文字以下。
- 空白だけを禁止する。
- ゲーム側で勝手に10文字へ切り詰めず、サーバー側と同じ上限を使う。
- 入力時に整えた値と、保存・再送・送信する値を同じにする。
- 表示名を利用者本人の識別番号として扱わない。同じ名前を別人が使える前提にする。
- ゲームごとに異なる名前規則を追加する場合は、マニフェストとゲーム固有文書へ理由を記録する。

名前の整え方を変更する場合は、ブラウザとSupabaseを同じ変更で更新します。

## 8. プレイ回数の共通ルール

プレイ回数は、次の時点で1回として数えます。

> 名前が確定し、開始ボタンが受け付けられ、ゲーム開始処理が成立した時点。

次はプレイ回数に含めません。

- ページを開いただけ
- 名前を入力しただけ
- チュートリアルを見ただけ
- 開始処理が通信エラーで成立しなかった場合
- 同じ開始処理の再送
- 結果画面を開き直しただけ

再戦ボタンから新しいゲームを開始した場合は、新しい1回として数えます。

各プレイには、ゲーム側で作る開始再送用の`start_id`と、Supabaseの`start_game_play_v1`が発行する`play_id`を一つずつ割り当てます。開始処理を再送する場合は同じ`start_id`を使い、Supabaseは最初に発行した同じ`play_id`を返します。ブラウザで作った番号を`play_id`として保存処理の正本にしてはいけません。

現行の`record_game_play`は`play_id`を受け取らないため、新規ゲームの標準実装として使いません。現在の`record_play_event`も、特定の結果種別と波数を前提にしており、すべてのゲームの開始記録には使えません。新規ゲームは、`start_game_play_v1`で開始し、返された`play_id`を`finish_game_play_v1`と`submit_score_idempotent_v1`へ渡します。

## 9. スコア送信の共通ルール

### 9.1 送信する時点

ランキング対象の終了条件が成立したら、結果画面を表示し、自動で送信を始めます。

利用者が「ランキング登録」ボタンを押した時だけ送る作りを禁止します。

どの終了結果を送るかは、`ranking_entries[].ranked_results`へ明記します。

例:

- `clear`
- `time_up`
- `game_over`
- `retire`

リタイアを送らないゲームは、マニフェストへ含めません。リタイアを送るゲームは、0点、途中点、到達数など、何を送るかをゲーム固有仕様へ書きます。

### 9.2 送信値

- スコアは安全な範囲の整数で送る。
- 小数の秒は、100倍または1000倍した整数で送る。
- `score_order`、`score_scale`、`score_decimals`をゲーム実装とSupabaseで一致させる。
- マイナス点を使うゲームでは、ゲーム側で勝手に0へ直さない。サーバー側の許容範囲も同時に決める。
- 送信する値と結果画面に表示する値を別々に計算しない。同じ確定結果から作る。

## 10. 同じ結果を二重登録しない仕組み

同じ送信を何度繰り返しても、記録件数とプレイ回数が1回分のままになる作りを必須とします。これを冪等性（idempotency）と呼びます。

### 10.1 必須の動き

- 一つの結果につき、一つの`submission_id`を作る。
- 最初の自動送信と手動再送で、同じ`submission_id`、名前、`game_slug`、スコア、`client_version`を使う。
- Supabase側で`submission_id`を一意に保存する。
- 同じ内容の再送には、最初の成功結果を返す。
- 同じ`submission_id`で内容が違う場合は、登録せず明確な競合エラーを返す。
- 成功した応答をブラウザが受け取れなかった場合でも、再送によって件数を増やさない。
- ページ再読み込み後に再送する場合も、保存済みの同じ`submission_id`を使う。

送信中・送信済みのメモリ上のフラグだけでは、この条件を満たしません。フラグは二度押しを減らすために使えますが、サーバーで受け付けた直後に応答だけ失われた場合を防げないためです。

### 10.2 現行処理の扱い

現行の`submit_score`は`submission_id`を受け取らないため、新規ゲーム向けの完成形として使いません。

`submit_score_once`という名前の処理は存在しますが、現在はサイノメの`game_slug`、クライアント版、契約版、非公開表へ固定されたサイノメ専用処理です。名前だけを見て全ゲームへ流用してはいけません。

新規ゲームは、次のどちらかを満たすまで`is_active = true`にしません。

1. 全ゲーム向けの同一送信対策付きRPCを使う。
2. ゲーム固有の同等RPCを作り、同一送信試験を通す。

既存ゲームの`submit_score`利用は、移行対象として扱います。ランキング処理を変更する時に、この規約へ移行します。

## 11. 送信状態と結果画面

送信状態は、画面文言ではなく、次の固定値で管理します。

| 状態 | 意味 | 再送ボタン |
|---|---|---|
| `idle` | まだ終了結果がない | 非表示 |
| `submitting` | 送信中 | 表示しても無効 |
| `submitted` | 登録確認済み | 非表示 |
| `retryable_failed` | 同じ内容で再送できる一時的失敗 | 表示して有効 |
| `permanent_failed` | 内容または設定を直さないと成功しない失敗 | 非表示 |

表示中の日本語を正規表現で読み取り、ボタンを有効・無効にすることを禁止します。状態を一つ持ち、文言、色、ボタン、診断表示をその状態から作ります。

### 11.1 再送ボタン

再送ボタンは次を必須とします。

- 押せる時は`disabled`を外す。
- 押せない時は見た目でも区別する。
- `min-height: 44px`以上にする。
- `touch-action: manipulation`を設定する。
- 押した直後に`submitting`へ変え、文言または表示が変わる。
- 連打しても同じ`submission_id`を一回だけ処理する。
- 成功後は非表示にする。
- 自動試験でクリック処理を確認する。
- iPhone Safariの本番URLで実際に押して確認する。

### 11.2 結果画面を壊さない

ランキング通信に失敗しても、結果、スコア、再戦、シェア、ホームへ戻る操作を残します。ランキング処理の例外で画面全体を止めたり、結果を消したりしてはいけません。

## 12. エラーの分け方と診断情報

利用者向けには短い日本語を表示し、調査用には構造化した情報を残します。

調査用情報には、最低限次を含めます。

- 処理名
- HTTP状態
- Supabaseのエラーコード
- `game_slug`
- `client_version`
- 公開版
- `submission_id`または`play_id`
- 発生時刻

公開用キー、認証情報、個人情報を診断表示へ含めません。

### 12.1 再送できる失敗

通信切断、時間切れ、HTTP 408、425、429、500番台など、同じ内容で再試行する意味がある失敗は`retryable_failed`にします。

### 12.2 再送しても直らない失敗

次は原則として`permanent_failed`にします。

- 未登録または無効な`game_slug`
- 名前、スコア、`client_version`、契約版の不一致
- 許可されていない終了結果
- 同じ`submission_id`で内容が違う
- 権限または受付設定の恒久的な不一致

HTTP番号だけで決めず、Supabaseのエラーコードと処理名も見て分類します。

## 13. ブラウザ通信の共通ルール

ゲームごとに異なる通信処理を手作業で増やさず、同じ検証済みの通信ラッパーまたは同等の共通実装を使います。

必須条件は次です。

- Supabase JavaScriptクライアントを使うか、共通RESTラッパーを使う。
- RESTを直接使う場合は、`apikey`、必要な`Authorization`、`Content-Type`を共通処理で付ける。
- ネイティブの`fetch`を変数やコンストラクタへ渡す場合は、`globalThis.fetch.bind(globalThis)`のように呼び出し先を固定するか、`fetchImpl.call(globalThis, ...)`で呼ぶ。
- 8秒程度の時間切れを設け、時間切れを再送可能として扱う。
- 応答の件数、型、`game_slug`、名前、スコアを検査する。
- 成功HTTPだけを見て登録成功と判断しない。
- ランキング通信が使えなくても、ゲーム本体は遊べるようにする。ただし、そのプレイがランキング対象外なら結果画面で明示する。

## 14. Supabase登録の手順

### 14.1 登録前に決める値

`ranking-manifest.json`で、少なくとも次を決めます。

- `game_id`
- 表示名
- 正式URL
- `client_version`
- `submission_mode`
- 代表ランキングの`game_slug`
- 各モードの`game_slug`
- `display_order`
- `top_ranking_type`
- `score_order`
- `score_unit`
- `score_scale`
- `score_decimals`
- 各表示ラベル
- 送信対象となる終了結果
- 開始記録RPC
- スコア送信RPC

### 14.2 最初は非公開で登録する

新規行は、最初に`is_active = false`で登録します。

この段階で次を確認します。

- すべての必須列が入っている。
- `game_slug`の重複がない。
- 有効なゲーム同士で`display_order`が重複しない予定になっている。
- 正式URLがマニフェストと一致する。
- スコア設定と表示ラベルが一致する。
- 使用するRPCが本番に存在する。
- 公開用ロールから必要なRPCだけを実行できる。
- 使わない旧`game_slug`が残っていない。

現在の本番には、公開中行だけを対象にした`display_order`の一意インデックスを追加済みです。公開前にも重複を検査し、登録時は非公開から始めます。

### 14.3 有効化試験

現行の`submit_score`は`is_active = true`のゲームだけを受け付けるため、完全な本番送信試験には短い有効化が必要です。

次の順で行います。

1. 非公開状態で、配備、マニフェスト、登録値、RPC、実験場表示処理を確認する。
2. 候補SHAと正式URLを固定する。
3. 対象行を有効化する。
4. 直ちに本番の受入試験を行う。
5. 一項目でも失敗した場合は、対象行を`is_active = false`へ戻す。
6. 全項目が通った場合だけ有効状態を維持する。

有効化と同時に別のコード変更を追加しません。

## 15. 実験場トップと詳細ランキング

### 15.1 実験場トップ

実験場トップは`public.games`を本番表示値として使います。

- `is_active = true`だけを表示する。
- `display_order`で並べる。
- マニフェストの`lab.representative_slug`を代表ランキングに使う。
- 一つの作品に複数モードがある場合、同じ作品カードを意図せず複数表示しない。
- 記録が0件でもカードを壊さない。
- 合計プレイ回数の意味を、各ゲームで変えない。

### 15.2 詳細ランキング

- URLは`ranking.html?game=game_slug`形式とする。
- 初回とベストを同じ`game_slug`で取得する。
- RPCが返した`rank_no`を使う。
- 同率を`index + 1`で作らない。
- スコア表示は`score_scale`と`score_decimals`に従う。
- 複数モードは、マニフェストに列挙されたモードだけを表示する。
- 廃止モードを固定配列から復活させない。

## 16. 公開前の受入試験

公開前には、同じ候補SHAと同じ正式URLで次を確認します。

### 16.1 自動確認

- [ ] `ranking-manifest.json`がJSON Schemaに合格する。
- [ ] 実装内の正式URL、`game_slug`、`client_version`がマニフェストと一致する。
- [ ] Supabase `public.games`の対象行がマニフェストと一致する。
- [ ] 有効な行の`display_order`に重複がない。
- [ ] 使用RPCが存在し、想定引数と戻り値を持つ。
- [ ] 同じ`play_id`を2回送ってもプレイ回数が1回だけ増える。
- [ ] 同じ`submission_id`を2回送っても記録件数とプレイ回数が1回だけ増える。
- [ ] 同じ`submission_id`で別スコアを送ると拒否される。
- [ ] 二度押しで送信要求が増えない。
- [ ] 失敗状態では再送ボタンが表示され、クリック処理が動く。
- [ ] 成功後は再送ボタンが消える。
- [ ] 同じ内部モジュールを複数のURLで読み込んでいない。
- [ ] GitHub Pagesの配備物に公開版と候補コードが含まれる。

### 16.2 本番URLでの確認

iPhone Safariから、次を実際に確認します。

- [ ] 正式URLを新しいタブで開く。
- [ ] 表示された公開版が候補版と一致する。
- [ ] 名前未入力では開始できない。
- [ ] 名前入力後に開始でき、プレイ回数が1回増える。
- [ ] 通常終了で送信中から成功へ変わる。
- [ ] Supabaseに対象の名前、`game_slug`、スコア、`client_version`が保存される。
- [ ] 実験場トップに記録が出る。
- [ ] 詳細ランキングに記録が出る。
- [ ] 通信を切った状態で終了すると、結果画面と再送ボタンが残る。
- [ ] 通信を戻して再送ボタンを押すと成功する。
- [ ] 再送後も同じ結果が1回分だけ数えられる。
- [ ] シェア文にはクエリなしの正式URLが入る。
- [ ] ページを通常再読込しても古い送信処理へ戻らない。

自動テストだけ、Supabase管理画面だけ、ソースコードだけの確認で本番試験を置き換えません。

## 17. 受入記録

受入記録には、最低限次を残します。

| 項目 | 内容 |
|---|---|
| ゲームリポジトリ | `owner/repository` |
| 候補コミット | 完全なSHA |
| 公開版 | HTMLの`chameleonjp-release` |
| 正式URL | クエリなしURL |
| マニフェスト版 | `schema_version` |
| `game_slug` | 対象すべて |
| `client_version` | 送信に使った値 |
| `submission_mode` | `shared`または`verified` |
| 試験日時 | タイムゾーンを含む |
| 端末 | 端末名、OS、ブラウザ |
| 試験名 | 本番確認に使った表示名 |
| 試験スコア | 内部整数と表示値 |
| Supabase確認 | 保存先と確認した行 |
| 実験場確認 | トップと詳細の結果 |
| 再送確認 | 失敗、再送、重複なしの結果 |
| 判定 | 合格、不合格、要再試験 |

「未実施」「確認できない」「おそらく成功」は合格にしません。

本番試験用の記録をランキングへ残したくない場合は、証拠を残した後で`ranking_status = 'hidden'`など、その保存方式に合う非表示処理を行います。調査に必要な履歴を先に削除しません。

## 18. 障害が起きた時の順番

ランキング障害では、推測で複数箇所を同時に直しません。

1. 候補SHA、正式URL、公開版、発生時刻、名前、`game_slug`、`client_version`を固定する。
2. ブラウザが送信要求を開始したか確認する。
3. Supabaseへ要求が到達したか確認する。
4. RPCのエラーコードと応答を確認する。
5. 保存表、実験場トップ、詳細ランキングの順に確認する。
6. 原因が配備物か、通信か、受付か、保存か、表示かを分ける。
7. 一つの原因に対して一つの修正を行う。
8. 同じ受入試験を最初からやり直す。

失敗中の記録を消して証拠をなくすこと、`game_slug`を試しに複数作ること、旧方式と新方式を同時に残すことを禁止します。

## 19. `shared`と`verified`の扱い

`submission_mode`は、登録前に決めます。

### `shared`

- 公開用キーで利用できる共通受付を使う。
- ゲーム側で計算したスコアを送る。
- 同一送信対策、入力検査、スコア範囲検査を必須とする。
- 表示名だけでは本人確認にならない。

### `verified`

- サーバー発行番号、署名、追加の受付条件などを使うゲーム向け。
- ゲーム固有の契約文書、移行SQL、停止・有効化手順、期限、再送条件を必須とする。
- `shared`用のクライアントへ途中でフォールバックしない。
- 公開途中で`shared`と`verified`を切り替えない。
- 方式変更は、マニフェスト、クライアント、Supabase、受入記録を一つの公開候補として切り替える。

複雑な受付方式を試験する場合でも、ゲーム公開とランキング公開を同時に行わず、受付を停止した状態で検証します。

## 20. 既存ゲームの移行

この規約を追加した時点で、すべての既存ゲームを直ちに停止しません。

ただし、次のいずれかを行うゲームは、この規約へ移行します。

- ランキング送信処理を変更する。
- `game_slug`、URL、スコア方式、送信対象結果を変更する。
- 再送機能を追加・修正する。
- `submission_mode`を変更する。
- 実験場へ新たに登録する。
- 長期にわたるランキング障害を修正する。

移行時は、最初にマニフェストを追加し、現在値との差を記録します。差を見つけても、先にSupabaseだけを上書きしません。
